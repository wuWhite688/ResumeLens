## 2. 实验怎么做的

1. 评测集：6 份中文简历 × 6 份 JD，组成 18 组配对（正 / 负 / 难负各 6 组）。文本在 `dataset/resumes/`、`dataset/jobs/`，配对与金标短语在 `dataset/pairs.json`。
2. 分块：生产配置 `chunkSize=900`、`overlap=120` 的真实 `TextChunker`。每份简历得到 **2** 个块（简历约 980–1440 字，会被 900 窗口切成技能+项目两块，教育会并进第一块）。
3. 金标：正样本块只要命中该岗位硬技能/对口项目短语即相关；负样本与难负样本相关块集合为空（见 `dataset/annotation-policy.md`）。应用结果见 `dataset/labeled-chunks.json`。
4. 检索：手工装配 `ResumeRagService`，embedding / 分块 / Lucene / 过阈逻辑全部走生产类。`ResumeChunkRepository` 用 JDK `Proxy` 内存实现（不改 `src/main/java`，也不依赖 MySQL）。`RagProperties` 除被扫描的 `minSimilarity` 外与生产一致：`topK=5`、`hybridEnabled=true`、`keywordBoost=0.035`、`dualQueryEnabled=true`。
5. 扫描：`0.35 … 0.80`，步长 `0.05`。每个阈值都重新调用 `retrieve()`（索引按 `sourceHash` 复用，查询 embedding 每次重算）。

指标定义：

- **块级**：预测正例 = `rawSimilarity >= 阈值`（含 `kept` 与 `over-topk`）。这测的是阈值本身，不是 Top-K。
- **配对级**：预测匹配 = `kept > 0`（prompt 里会有证据；否则走 0 分兜底）。正样本应为匹配，负/难负应为不匹配。
- **boostWouldCross**：`raw < 阈值 ≤ boosted`。用来验证「关键词 boost 不得越阈」。

## 6. 三个问题

### 6.1 阈值调低到 0.45 会怎样？

**比 0.55 更糟，而且 0.35–0.50 完全分不开。**

- 18 组配对全部 `kept>0`，配对 F1 只有 **0.500**。
- 负样本 6/6 误放行（12 块），难负 6/6 误放行（12 块）。
- 块级精确率只有 0.306：每放过 1 个真正相关块，大约同时放过 2 个不该进 prompt 的块。
- 和 0.55 相比，0.45 只是把 N3（前端×会计，max raw=0.5343）也放进来了。污染 prompt 的问题在 0.55 已经很严重，再降低只会更差。

### 6.2 阈值调高到 0.70 会怎样？

**在这套评测上，0.70 没有漏判正样本，反而第一次把负样本和难负全部挡住。**

- 正样本 6/6 仍有证据，均 kept=2.00，gold 召回仍是 1.000。没有一组走到 0 分兜底。
- 负样本误过阈块 0，难负误过阈块 0，配对 F1 = **1.000**，块 F1 = **0.957**。
- 再升到 **0.80** 才开始伤正样本：P2 / P3 / P4 各丢掉 1 个金标块（gold 召回 0.727，均 kept 降到 1.50）。配对级仍 6/6 有证据，但证据变少。

预期里「0.70 会让正样本证据变空」**没有在这组中文对口样本上发生**。正样本 raw 下限大约 0.75–0.80（P2 较弱块 raw=0.7510），所以 0.70 仍安全，0.80 开始掉块。

### 6.3 0.55 是不是合理选择？

**不是。在这组真实 retrieve 数据上，0.55 明显偏低。**

0.55 时：

- 配对 F1 **0.522**，块 F1 **0.512**。
- 正样本 6/6 有证据（这一点没问题）。
- 负样本 **5/6** 仍把无关块送进 prompt（8 块），只有 N3 前端×会计被挡住。
- 难负 **6/6** 全部泄漏（12 块）。Java 后端去匹配 React JD（H1，max raw=0.6900）会带着 2 块「证据」去让 LLM 打分。
- 若误用 boosted 过阈，还会再放行 4 块（N3 的 raw 0.52–0.53、boosted 0.60–0.63）。**「boost 不越阈」这条设计是对的，也确实起了作用**；但 0.55 本身挡不住语义上已经偏高的跨岗/近岗块。

### 6.4 最终取值：0.72（按块级边界校准）

0.70 / 0.72 / 0.75 三个点的汇总指标**完全相同**（块 F1 0.957、配对 F1 1.000、gold 召回 1.000、负样本与难负误放行均为 0），因此不能靠汇总表在三者之间做选择，必须回到**块级边界**：

| 边界 | 来源 | raw |
|------|------|----:|
| 下界：最高的非金标块（难负） | H1 chunk0「教育」 | **0.690011** |
| 上界：最低的金标相关块 | P2 chunk1「项目」 | **0.751004** |

可分离区间因此是 **(0.690011, 0.751004)，宽度仅 0.060993**，中点 **0.720508**。

- 取 **0.70**：距下界只有 0.0100，稍微更相近的跨方向简历就会重新漏进 prompt。
- 取 **0.75**：距上界只有 0.0010，几乎贴着 P2 chunk1，稍弱一点的对口简历就会掉证据。
- 取 **0.72**：距两侧分别为 0.0300 / 0.0310，是这组数据上余量最均衡的取值。

注意原始扫描用的是 0.35–0.80 步长 0.05 的网格，**该网格恰好跨过这段 0.061 宽的区间**，两端的 0.70 与 0.75 都紧贴边界，因此补测了 0.72 这个校准点（见 `sweepThresholds()`）。

据此已将生产默认值由 `0.55` 改为 **`0.72`**（`RagProperties#minSimilarity` 与 `application.properties`），阈值仍可通过 `RAG_MIN_SIMILARITY` 覆盖。改动后 `.\mvnw.cmd -B verify` 为 **30 项 / 0 失败 / 5 跳过 / BUILD SUCCESS**。

> **适用范围（务必连同数字一起引用）**：本校准集只有 18 组配对、11 个金标块，简历与 JD 均为构造文本，**没有独立的 holdout 集**，因此这是一次小规模校准而非严格评测，0.72 也不应被当作「最优阈值」的普遍结论。它只对当前的 embedding 模型（`gte-multilingual-base-int8`）与分块配置（`chunkSize=900` / `overlap=120`）成立——换模型、换分块或换语料都必须重跑本实验重新校准。

## 8. 其它发现（仅记录，未针对它们改动代码）

> 本次实验带来的唯一代码改动是 6.4 节的阈值默认值 `0.55 → 0.72`；下列各条**均未**改动。

1. **这颗中文 GTE 的余弦值整体偏高。** 护士简历对 Java JD 也能到 0.59–0.62，Java 对 React 能到 0.69。英文回归测试里「相关 ≥ 0.70、间隔 ≥ 0.20」不能直接平移到中文简历/JD。
2. **关键词抽取会把 JD 里的 `1.` / `2.` / `3.` 当成 token**（`TOKEN_PATTERN` 允许数字和点）。boost 列表里经常出现这些编号，对中文编号任职要求不健康，但本次 boost 不能越阈，所以没有改变谁过线。
3. **`chunkSize=900` 对这份长度的中文简历偏大**：教育、技能、第一段工作经历常常挤在同一块里，阈值实验的「块级」粒度偏粗。这是生产分块行为，不是实验简化。
4. P5 第 2 块（社区门诊+自我评价）对心内科 JD 仍有 0.8408 raw。同职业不同科室的文本，单靠余弦很难切开。
